01 — The Problem

Why does this exist?

Imagine you're running a small software company where the developers are CLI-based AI agents — Claude, Codex, OpenCode — each running in their own terminal pane. They're great at writing code in isolation.

But they're terrible at:

  • Coordinating with each other
  • Recovering when they crash
  • Knowing when to ask for help
  • Staying in sync with the project

Firstmate is the orchestration layer — the "first mate" — that makes a fleet of agents actually work as a team. It assigns work, checks progress, handles failures, merges PRs, and talks to the captain (you).

02 — The Core Insight

The one idea

A zero-token bash watcher classifies wake events and only bothers the AI captain when something actually needs human judgment. Everything else stays silent.

This is the system's heartbeat. Without it, the captain would drown in status updates from every agent. The watcher runs in pure bash — no LLM calls, no token costs — and triages events into "actionable" vs "noise."

03 — The Architecture

Three layers, each building on the one below

1 The Watcher bin/fm-watch.sh ▼

A lightweight bash process sitting in the background, polling your terminal panes. It classifies what it sees into:

⚡

Actionable wakes — things the captain needs to see: PRs ready for review, failed checks, stale agents, decisions needed.

🔇

Absorbed wakes — noise silently discarded: routine progress notes, agents still working fine.

Events are written to a durable queue (state/.wake-queue) before state advances, so if the watcher restarts, no events are lost.

🧠

System design lens: Think of it as a message broker with built-in deduplication and priority routing. The queue is durable for crash recovery.

2 Runtime Backends bin/fm-backend.sh ▼

The session providers — the actual terminal environments where agents run. Each has different capabilities for detecting busy states, submitting text, or reading output.

Backend Status What it is
tmux Verified Classic terminal multiplexer — the default
herdr Experimental Native agent-state awareness (working/idle/done/blocked)
zellij Experimental Rust-based tmux alternative
orca Experimental Owns both worktree and terminal lifecycle
cmux Experimental GUI-first, macOS-only
🧠

Web dev analogy: These are like different web servers (nginx, Apache, Caddy) behind a load balancer. The abstraction layer routes operations to the right one.

04 — Safety

Worktrees, not your checkout

Crewmates never intentionally touch your project clone. Firstmate uses git worktrees — isolated copies of the repo that share history but have independent working directories.

🧠

Why it matters: If an agent corrupts its worktree, you just discard it — no damage to your working copy. It's like sandboxed containers for code.

⚠ The Danger Zone

The one place a naive change breaks everything is worktree isolation. If you accidentally let an agent write to the primary checkout instead of an isolated worktree, you could corrupt the captain's working copy. That's why fm-spawn.sh refuses to launch unless the path is a real worktree root distinct from the primary.

05 — Scaling

Optional secondmates

A secondmate is a persistent domain supervisor with its own isolated home, project clones, and charter. Think of it as a team lead for a specific area — issue triage, feature development, testing.

Key properties:

  • Idle by default — waits for routed work, never self-initiates
  • Has its own backlog, state, and project clones
  • Can run on a different harness than crewmates
  • Converges conservatively to the primary's version at launch
🧠

Multi-agent lens: This is the delegation pattern you mentioned clicking on — agents delegating to other agents. A secondmate delegates to its own crew, and the firstmate delegates to secondmates.

07 — Watcher Deep Dive

How the watcher decides what to escalate

This is the brain of the system. Every event that hits a pane flows through this decision tree:

Event detected in a pane
Is it a "no-verb" signal? (working note, bare turn-ended)
YES → Is crew provably working? (active no-mistakes run, backend busy)
YES → ABSORB — silent, no queue record
NO → ESCALATE — actionable wake
Is it captain-relevant status? (failed, decision needed)
YES → ESCALATE — immediately
Is the pane stale? (no activity for N seconds)
YES → Is crew provably working?
YES → wait FM_STALE_ESCALATE_SECS, then ESCALATE
NO → ESCALATE — stale wake
Is it a declared external wait? (paused)
YES → ABSORB — re-surface on longer cadence
Is it a heartbeat backstop?
YES → REVIEW — whole fleet, reconcile suspicious tasks
💡

The pattern to steal: "Classify then escalate" — your AI assistant shouldn't bother you with every tool call result. Absorb routine outputs, only surface things that need your judgment.

08 — Dispatch

Intelligent task routing

This is how firstmate decides which AI agent handles which task. It's a judgment-based system, not rigid rules.

1
Task arrives

Captain says "fix the auth bug" or "add a new endpoint"

2
Read natural-language rules

Firstmate reads config/crew-dispatch.json — rules like "for security audits, use the most capable model"

3
Match best rule to task

LLM reads the rules and matches them against the incoming task description

4
Resolve concrete axes

Outputs: --harness, --model, --effort

5
Spawn agent

Pass resolved profile to fm-spawn.sh

🧠

System design lens: This is a content-based router in a message queue — except the matching is done by an LLM reading natural language rules, not by regex or header matching.

09 — Safety Boundary

No-mistakes gate authority

Firstmate can dispatch agents to work on itself — the firstmate repo. That creates a weird problem: the gate that validates code changes runs inside a checkout that also contains the captain's identity instructions.

⚠ The Authority Problem

An agent could potentially read the captain's instructions and use them to escalate its own privileges during validation. The solution: authority isolation via environment markers.

.no-mistakes.yaml

Sets disable_project_settings: true — but only honored from the trusted default-branch copy

fm-spawn.sh

Refuses to mutate fleet state when the gate environment marker is present

fm-send.sh

Same refusal — prevents an agent from steering other agents while inside the gate

fm-teardown.sh

Same refusal — can't clean up while inside the validation checkout

🧠

Defense in depth: Even if an agent somehow got control of the validation pipeline, it couldn't use that position to escalate its own privileges. The environment marker acts like a capability token that can't be forged.

⏱ Bounded Follow-ups

3-post cap per request, 7-day window. Longer tasks get an acknowledgement first, then milestone follow-ups.

🛡 Safety Rails

Destructive/irreversible asks are escalated for trusted-channel confirmation — never executed from public mentions.

🖼 Image Support

Visual artifacts (PNG, JPEG, GIF, WebP) attached to replies via the relay's media endpoint.

🧵 Split Replies

Long answers split into bounded, numbered threads. Preserves code blocks and paragraph boundaries.

💡

Pattern for your assistant: This is a production-grade "public trigger → private work → public result" loop. Exactly the pattern you'd need for an assistant that responds to external signals but does work internally.

11 — Memory

Where knowledge lives

Firstmate has a strict policy about where different types of knowledge go. Nothing is dumped into one flat file — every piece of knowledge has a most-specific owner.

Knowledge Type Destination Why
Captain preferences data/captain.md Domain-local, evolves over time
Shared captain prefs data/captain-shared.md Inherited by secondmates
Fleet operational facts data/learnings.md Curated, dated, evidence-backed
Project-intrinsic knowledge project/AGENTS.md Lives with the code
Task-scoped notes Backlog item Dies with the task
Generalizable knowledge Shared docs via PR Benefits everyone
💡

Pattern for your assistant: This is a memory routing table. Your assistant should similarly classify incoming knowledge and route it to the right storage tier — not dump everything into one flat file.

Inspect-then-update

Memory writes don't just append — they read the current destination first, then rewrite or prune matching bullets in place. This prevents rot from infinite appending.

12 — Resilience

Restart-proof by design

Conversation memory is ephemeral. Durable state lives on disk. If firstmate crashes and restarts, it reads durable state, reconciles with live backend state, and carries on.

💾 Session Backends

tmux panes, herdr sessions — terminal state persists across restarts

📋 Run Records

No-mistakes validation history — what passed, what failed, and why

📝 Status Event Logs

Append-only wake events — the full history of what happened

📁 Local Markdown

data/ directory — captain prefs, learnings, project registry

🧠

For your QA goal: This is the "state machine with durable transitions" pattern. Every important state change is persisted, so recovery is always possible. Your testing framework should work the same way — test state should be reconstructable from durable records.

Check Yourself

Q1 What's the core job of the watcher, and why is "zero-token" important?

The watcher triages wake events so the captain (an LLM with token costs) only processes actionable ones. "Zero-token" means the watcher itself runs in pure bash with no LLM calls — it's cheap to run constantly.

Q2 You're adding a new terminal backend. Which files do you need to touch, and which stay unchanged?

You'd add bin/backends/yourbackend.sh and update bin/fm-backend.sh for selection logic. The watcher (fm-watch.sh) stays unchanged — it already falls back to terminal-tail regex for unknown backends.

Q3 What happens if the watcher dies while agents are working? How does firstmate recover?

The watcher writes events to a durable queue before advancing state. On restart, fm-wake-drain.sh replays queued events. The guard also warns if the watcher stops running while tasks are in flight.

Q4 Why does firstmate use git worktrees instead of branches in the primary checkout?

Worktrees give agents an isolated copy of the repo without duplicating the full history. The primary checkout stays clean. If an agent corrupts its worktree, you just discard it — no damage to the captain's working copy.

Q5 A ship task fails validation. What's the difference between a no-mistakes project and a direct-PR project at this point?

no-mistakes runs the full validation pipeline (review, tests, lint, docs, push, PR, CI) before the PR is considered done. direct-PR opens the PR immediately without that pipeline — faster but less safe.

Q6 A no-verb "working" signal arrives. Under what condition does the watcher absorb it vs escalate?

The watcher checks if the crew is provably working — an active no-mistakes run on the crew's branch, or a backend busy signature. If provably working → absorb. If not → escalate as actionable.

Q7 Why is the dispatch file written in natural language instead of rigid rules?

Because task descriptions are messy human language. An LLM reading "for security audits, use the most capable model" can match it against a vague task like "check the auth system" better than a regex ever could. The judgment is the feature, not a bug.

Q8 What prevents an agent inside the no-mistakes gate from escalating its own privileges?

Three independent refusals: fm-spawn.sh, fm-send.sh, and fm-teardown.sh all check for the gate environment marker and refuse to mutate fleet state when it's present. Plus .no-mistakes.yaml only works from the trusted default branch.

Q9 How does X mode handle a task that takes longer than one reply?

First reply is an acknowledgement. Then fm-x-link.sh records the request in the task's metadata. Later milestone and completion wakes use fm-x-followup.sh to post up to 3 follow-ups through the relay, ending with a --final one that clears the link. All bounded by a 7-day window.

Q10 Why does firstmate use "inspect-then-update" for memory writes instead of just appending?

Because infinite appending causes rot. Reading the current destination first lets you rewrite or prune matching bullets in place — keeping the knowledge file curated rather than bloated. Same principle as database upserts vs blind inserts.
